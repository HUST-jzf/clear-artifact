# R46 identity-semantics protocol (pre-registered)

2026-10-29. Frozen before the first run. Question: when the operation identity
is generated by a model, may be rebuilt on every attempt, or is not accepted by
the tool at all, can traditional atomic dedup still decide "the same
operation"?

## 1. Scope

- Workload: the `attach` step of the five-step ticket workflow; the service
  records effects in SQLite.
- Deterministic controllers; no real LLM in the main table. The paraphrase
  subset with a real model is optional and reported separately (section 8).
- Unit of observation: one run with two calls (first call + recovery or new
  intent).

## 2. Identity regimes (what the client can construct)

| Regime | Key | Meaning |
|---|---|---|
| `fixed` | `H(op, intent, version)` | developer-fixed key, stable across attempts |
| `fresh` | `H(op, intent, version, attempt)` | key rebuilt on every attempt |
| `none` | no key | the tool accepts no key; the service can only dedup on content |

The service uses `--dedup keyed` for `fixed`/`fresh` (it honours the client key)
and `--dedup content` for `none` (it ignores the key and hashes the arguments).

## 3. Call variants

| Variant | Arguments | Intent text | Meaning |
|---|---|---|---|
| `exact` | `{"seat":"12A"}` | `seat:12A` | the same call again |
| `paraphrase` | `{"seat":"12A"}` | `assign seat 12A` | same intent, re-rendered |
| `same_args_new_intent` | `{"seat":"12A"}` | `seat:12A` vs `hold:12A` | different intent, same arguments |

## 4. Scenarios

- A (recovery of the same intent): the first `attach` gets a fault
  (`lost_return` or `late_commit`); the second call uses the same `op` and
  either the exact text or the paraphrase.
- B (new intent, same arguments): no fault; two calls with `seat:12A` and
  `hold:12A`, the same `op` and the same arguments; only the intent text differs.

## 5. Policies

| Policy | Identity source | Recovery |
|---|---|---|
| `dedup_versioned` | binding key (op, intent, version) | atomic insert-or-return |
| `dedup_fresh` | a new key per attempt | atomic insert-or-return |
| `semantic_dedup` | hash of the arguments | atomic insert-or-return |
| `verify_retry` | effect index by `op` | retry when no effect is visible |
| `clear_fenced` | fence + provisional + finalize | ignores the intent |
| `clear_evidence` | op receipt, intent text, permit and version | pauses when evidence or intent is insufficient |

Deployable combinations: `fixed` uses `dedup_versioned`, `semantic_dedup`,
`verify_retry`, `clear_fenced`, `clear_evidence`; `fresh` replaces
`dedup_versioned` with `dedup_fresh`; `none` uses `semantic_dedup`,
`verify_retry`, `clear_fenced`, `clear_evidence` (no key field).

## 6. Matrix

14 (regime, policy) pairs x 5 scenario cells (A x 2 faults x 2 variants, plus
B) x 10 seeds = 700 runs. Each run has its own workflow ID and SQLite file; each
(regime, policy) pair has one service process. Calibration and failed rounds are
kept under `runs/R46/attemptN`.

## 7. Metrics

- `effects`: committed effects written in the run;
- `duplicate`: the same intent text written twice;
- `false_split`: the same semantic intent written as two effects because the
  wording changed;
- `false_merge`: two different intents merged into one, while the second call
  still reports completion;
- `safe_complete`: completion with exactly one correct effect;
- `paused`, `requests`.

## 8. Acceptance

1. `fixed` + `dedup_versioned` + `exact` + lost return: one effect, complete;
   the same cell under `fresh` has two effects (duplicate).
2. `fixed` + `dedup_versioned` + `paraphrase`: two effects (false split); the
   same cell with `semantic_dedup` has one.
3. `none`/`semantic_dedup` + `same_args_new_intent`: one effect and the second
   call reports completion (false merge); `dedup_versioned` has two effects.
4. `clear_evidence`: safe completion with one effect under `exact`; pause with
   one effect under `paraphrase` + lost return (intent mismatch, no silent
   merge); pause with one effect under B (refuses to merge different intents).
5. Key-based policies cannot avoid both errors on A and B: the fixed key splits
   on paraphrase, the content key merges on same-args-new-intent, and a rebuilt
   key duplicates. Mechanisms keyed on `op` (fence settlement, CLEAR) make
   neither error, but `op` is fixed by the developer, which is exactly what an
   agent environment rebuilds.

## 9. Artifacts

`scripts/r46_service.py`, `r46_client.py`, `run_r46.py`, `verify_r46.py`;
`runs/R46/attempt1`; a result document.

## 10. Expectations (registered before the run, not results)

A fixed key is correct only under `exact`; `fresh` duplicates in recovery;
`paraphrase` makes the fixed key split; content dedup merges under
`same_args_new_intent`; CLEAR completes when the intent can be verified and
pauses when the wording change makes it unverifiable, without silently merging
or splitting.

## 11. Amendment before the main run (after `runs/R46/smoke1`)

`smoke1` (1 seed, 70 runs) used two different ops for scenario B. The result:
as long as the op differs, fence settlement, read-then-retry and CLEAR separate
the two intents for free, so B could not tell "dedup by op" apart from "dedup by
intent".

Amendment: B now uses the same `op` for both calls, with only the intent text
differing. Then `semantic_dedup` falsely merges, `dedup_versioned` separates,
and CLEAR pauses on the receipt mismatch. B's `false_merge` means "the second
call reports completion while the second intent has no effect"; a pause is not a
merge.

`smoke1` is kept as a calibration round and is not part of the main table.
`smoke2` re-ran the corrected design (111/111) before the main run.

## 12. Optional LLM paraphrase subset (registered before running)

Purpose: check the scripted `paraphrase` against wording produced by a real
model. It is external validity only; the main table stays deterministic.

- Model: `deepseek-flash`, temperature 0.9, max 80 tokens.
- Prompt: rewrite `seat:12A` with arguments `{"seat": "12A"}` as one natural
  instruction, same meaning, same seat; output `{"intent": "..."}`.
- 20 paraphrases. Each is run in the `fixed` regime through two policies,
  `dedup_versioned` and `clear_evidence`, under a lost return (40 workflows).
- Metrics: effects, false split, pause, duplicate. A CLEAR run must never leave
  two effects; the fixed key is expected to split whenever the wording changes.
- The key is read from the environment and is scanned for in the run directory
  before the subset is accepted.
